# Adrobot — Software Specification

**Версия:** 1.0  
**Основание:** исходное ТЗ, скриншоты и транскрипция видео заказчика  
**Срок выполнения тестового:** 5 дней  
**Цель:** реализовать рабочую обёртку над Keitaro с двумя независимыми разделами.

## 1. Назначение проекта

Adrobot — веб-приложение для автоматизации двух операций с рекламным трекером Keitaro:

1. **Создаватор (Creator)** — автоматическое создание кампаний с заданными правилами маршрутизации.
2. **Редактор (Editor)** — управление офферами существующих кампаний, распределением их весов и публикацией изменений.

Приложение должно взаимодействовать с реальным Keitaro через Admin API.

## 2. Технологический стек

### Обязательные технологии

- Python.
- FastAPI.
- SQLAlchemy.
- База данных для хранения состояния редактора.

Frontend — на усмотрение разработчика.

### Выбранная архитектура

Единое веб-приложение, modular monolith:

- Один backend.
- Один порт.
- Общий Keitaro API client.
- Независимые бизнес-модули Creator и Editor.
- Общая конфигурация и доступ к базе данных.

Маршруты:

- `/creator`
- `/editor`
- `/` перенаправляет на `/creator`

Для миграций базы данных рекомендуется Alembic.

Существующую архитектуру проекта сохранять, если она соответствует требованиям.

## 3. Creator — Создаватор

### 3.1. Интерфейс

Одна компактная форма, соответствующая макету заказчика.

Три поля:

| Название | Поведение |
|---|---|
| Name | Название создаваемой кампании |
| Geo | Код или несколько кодов стран, например `MX,AU,RO` |
| Offer | Поиск существующего оффера с автодополнением |

Одна кнопка — **Create / Создать**.

Поиск оффера выполняется через backend, который обращается к Keitaro API.

Пользователь видит название оффера, приложение использует его ID.

Коды стран нормализуются и проверяются перед отправкой.

### 3.2. Создание кампании

После нажатия Create приложение:

1. Проверяет введённые данные.
2. Находит выбранный оффер.
3. Определяет домен, группу и источник.
4. Создаёт кампанию через API Keitaro.
5. Создаёт два потока с правильным порядком.
6. Возвращает ID кампании и результат операции.

### 3.3. Первый поток

- Имеет фильтр по введённым GEO.
- Перехватывает пользователей из указанных стран.
- Перенаправляет их на `https://www.google.com/`.
- Имеет приоритет перед вторым потоком.

Если указаны несколько GEO, фильтр должен принимать пользователя из любой указанной страны.

### 3.4. Второй поток

- Обрабатывает оставшихся посетителей.
- Перенаправляет на выбранный оффер Keitaro.
- При первоначальном создании содержит один выбранный оффер.

Маршрутизация должна соответствовать настройкам Keitaro, а не имитироваться на стороне Adrobot.

### 3.5. Домен, группа и источник

По ТЗ все три параметра должны быть настроены, но не требуется показывать их в форме.

В примере заказчика:

- Домен: `https://in.posdk.xyz/`.
- Группа: `FORTESTS`.
- Источник: `FORTESTS`.

Эти значения рассматриваются как предпочтительная конфигурация, а не обязательные ID.

**Выбранная логика реализации:**

- Получать объекты через API.
- Искать предпочтительные значения.
- Если указанный домен отсутствует, использовать первый пригодный домен из доступных по стабильному порядку.
- Не назначать заведомо неработающий домен.
- Группу и источник определять по конфигурации и фактическим данным API.
- Если обязательный объект найти нельзя — сообщать об ошибке.

Создание новых доменов, групп и источников автоматически не является требованием ТЗ.

### 3.6. Ошибки

Необходимо обрабатывать:

- Незаполненные поля.
- Некорректные GEO.
- Несуществующий оффер.
- Отсутствие доступного домена.
- Ошибки авторизации Keitaro.
- Ошибки создания кампании или потоков.
- Частично завершённую операцию.

Нельзя выводить сообщение об успешном создании, если один из обязательных шагов завершился ошибкой.

## 4. Editor — Редактор

### 4.1. Назначение

Редактор воспроизводит бизнес-логику существующей обёртки заказчика, продемонстрированной в видео.

Он должен поддерживать:

- Получение потоков кампании.
- Просмотр офферов внутри потоков.
- Поиск и добавление офферов.
- Удаление офферов с сохранением истории.
- Восстановление удалённых офферов.
- Автоматический перерасчёт весов.
- Закрепление весов (Pin).
- Публикацию изменений (Push).
- Отмену неопубликованных изменений (Cancel).
- Синхронизацию с изменениями, внесёнными непосредственно в Keitaro.

### 4.2. Fetch Streams

При нажатии **Fetch Streams** приложение:

1. Запрашивает все потоки выбранной кампании.
2. Получает состав офферов для потоков, содержащих офферы.
3. Синхронизирует полученные данные со своей базой.
4. Отображает потоки и их текущее состояние.

**Особое правило из видео:**

Потоки без офферов тоже должны присутствовать в интерфейсе.

Однако для них не требуется отображать или разбирать фильтры, URL редиректов и прочие внутренние настройки.

То есть поток с редиректом на Google отображается как поток, но без подробного анализа его содержимого.

### 4.3. Добавление оффера

Пользователь выбирает поток и открывает поиск офферов.

Поиск должен обращаться к общему списку доступных офферов Keitaro.

Допускается поиск по названию или ID.

После выбора и нажатия Add:

- Оффер добавляется в рабочее состояние потока.
- Веса активных офферов автоматически пересчитываются.
- Поток получает статус неопубликованного.
- Изменения пока не отправляются в Keitaro.

**Пример из видео:**

До добавления три оффера, каждый с приблизительно равной долей — около 33,33%.

После добавления четвёртого оффера каждый получает 25%.

### 4.4. Состояние неопубликованных изменений

После любой операции, меняющей состав офферов или их веса, поток должен быть визуально отмечен как изменённый.

По примеру заказчика:

- Белый — нет неопубликованных изменений.
- Жёлтый — имеются неопубликованные изменения.
- Серый оффер — удалён или находится в архиве.

Рабочее состояние должно храниться с использованием SQLAlchemy и сохранять информацию, необходимую для корректной отмены и публикации.

### 4.5. Push

При нажатии **Push** приложение:

1. Проверяет рабочее состояние потока.
2. Проверяет корректность весов.
3. Формирует запрос на обновление через Keitaro API.
4. Отправляет только предусмотренные изменения.
5. Получает подтверждение API.
6. Синхронизирует опубликованное состояние.
7. Убирает индикатор неопубликованных изменений.

**Основное правило:** добавление или удаление оффера в интерфейсе не должно автоматически менять Keitaro до Push.

Изменения в потоках без офферов и посторонние настройки кампании должны сохраняться без непреднамеренной модификации.

### 4.6. Cancel

Кнопка **Cancel** отменяет все неопубликованные изменения выбранного потока.

После Cancel:

- Новые, ещё не опубликованные привязки офферов удаляются из рабочего состояния.
- Удаления, которые ещё не были опубликованы, отменяются.
- Веса возвращаются к последнему опубликованному состоянию.
- Индикатор изменений исчезает.
- Keitaro не изменяется.

Локальная база должна быть приведена к согласованному состоянию без потери истории ранее опубликованных удалений.

### 4.7. Remove

При нажатии **Remove**:

- Оффер помечается как удаляемый.
- Его вес становится 0%.
- Остальные активные веса пересчитываются.
- Оффер становится серым.
- Поток отмечается как неопубликованный.

После Push оффер удаляется из активного состава потока Keitaro.

**Но из базы Adrobot он не удаляется.**

Связь с его историей сохраняется в архиве, чтобы можно было выполнить Bring Back.

### 4.8. Bring Back

Для удалённого оффера должна быть доступна кнопка **Bring Back**.

При нажатии:

- Оффер возвращается в рабочий активный состав.
- Его вес пересчитывается.
- Поток становится неопубликованным.
- После Push оффер снова появляется в Keitaro.

Удаление и восстановление должны работать даже после повторного открытия редактора.

### 4.9. Внешние изменения в Keitaro

Редактор должен корректно обрабатывать ситуацию, когда пользователь меняет кампанию напрямую в админке Keitaro.

Сценарий из видео:

1. Adrobot получил три оффера из потока.
2. Пользователь удалил два оффера непосредственно в Keitaro и сохранил изменения.
3. Пользователь нажал Fetch Streams в Adrobot.
4. Приложение обнаружило, что два ранее известных оффера отсутствуют.
5. Вместо полного удаления локальных записей оно переводит их в статус Removed.
6. Офферы остаются серыми и доступны для Bring Back.

Это важное требование синхронизации.

Нельзя заменять весь локальный набор данных новым ответом API с потерей истории.

Если имеются неопубликованные локальные изменения, Fetch Streams не должен незаметно уничтожать их — необходимо предусмотреть безопасную политику разрешения конфликта.

### 4.10. Pin — закрепление веса

Пользователь может закрепить вес оффера.

Пример:

- Offer A — 25%, закреплён.
- Offer B — 37,5%.
- Offer C — 37,5%.

При последующем добавлении или удалении офферов:

- Вес A остаётся 25%.
- Веса незакреплённых офферов перераспределяются.
- Общая сумма активных весов должна оставаться 100%.

Информация о закреплении сохраняется в базе приложения.

### 4.11. Алгоритм перераспределения весов

Определения:

- `P` — сумма закреплённых весов.
- `N` — количество незакреплённых активных офферов.
- `R = 100 - P` — оставшаяся доля.

Если `N > 0`, каждому незакреплённому офферу назначается доля `R / N` с учётом допустимой точности.

Если `P > 100`, операция должна завершиться ошибкой валидации.

Если `N = 0`, сумма закреплённых весов должна составлять 100%, иначе публикация невозможна.

Офферы со статусом Removed не участвуют в распределении и имеют 0%.

Использовать точные десятичные вычисления, не допускать накопления ошибок float.

При округлении применять детерминированный алгоритм, гарантирующий сумму 100% в точности, допускаемой API.

### 4.12. Поиск офферов

Офферы загружаются через Keitaro Admin API.

В реальном режиме нельзя подмешивать фиктивные офферы.

Если доступен только один оффер, приложение должно корректно работать с единственным результатом.

Отдельные тесты с несколькими офферами должны выполняться с использованием mock API или изолированного Demo-режима.

## 5. Хранение данных

SQLAlchemy используется для хранения состояния редактора.

Минимально необходимая информация:

- Идентификаторы кампаний и потоков Keitaro.
- Локальное представление офферов и их связей с потоками.
- Последнее опубликованное состояние.
- Неопубликованные изменения.
- Веса офферов.
- Статусы Active / Removed.
- Закреплённые веса.
- История, необходимая для Bring Back и внешней синхронизации.

Конкретная схема таблиц выбирается разработчиком.

Необходимо обеспечить целостность записей и поддержать миграции базы данных.

## 6. Требования к API-интеграции

Все обращения к Keitaro выполняются через backend.

Использовать общий API-клиент.

Необходимо:

- Учитывать фактическую версию Keitaro.
- Проверять форматы запросов и ответов по документации.
- Обрабатывать сетевые ошибки.
- Обрабатывать ошибки прав доступа.
- Не логировать API-ключи.
- Не отправлять секреты на frontend.
- Не изменять объекты Keitaro за пределами выбранной операции.

Нельзя предполагать, что API возвращает все офферы, если аккаунт ограничен по правам.

## 7. Интерфейс

Существующий визуальный стиль Adrobot сохранить.

Структура:

**Создаватор | Редактор**

Creator должен соответствовать простоте макета заказчика.

Editor может иметь собственный интерфейс при условии, что все необходимые операции доступны и работают.

В Editor обязательно показывать:

- Список потоков.
- Активные офферы и их веса.
- Архивные офферы.
- Индикатор неопубликованных изменений.
- Элементы управления Add, Remove, Bring Back, Pin, Push, Cancel и Fetch Streams.
- Сообщения об ошибках.

Не добавлять новые возможности в ущерб работе обязательной логики.

## 8. Автоматизированные тесты

### Creator

- Создание с одним GEO.
- Создание с несколькими GEO.
- Правильный фильтр первого потока.
- Корректный редирект на Google.
- Второй поток с выбранным оффером.
- Автоматическое назначение домена, группы и источника.
- Невалидные входные данные.
- Отсутствующие объекты Keitaro.
- Ошибка частичного создания.

### Editor

- Fetch Streams загружает потоки с офферами и без них.
- Поток без офферов не требует анализа внутренних настроек.
- Добавление четвёртого оффера перераспределяет веса на 25% каждому.
- До Push удалённые данные Keitaro остаются неизменными.
- Push сохраняет офферы и веса через API.
- Cancel полностью отменяет неопубликованные изменения.
- Remove переводит оффер в архив, вес 0%.
- Bring Back возвращает архивный оффер.
- Fetch Streams обнаруживает внешнее удаление и сохраняет историю.
- Pin сохраняет закреплённый процент.
- Все активные веса корректно суммируются до 100%.
- Ошибочные и конфликтные изменения обрабатываются безопасно.

Все автоматические тесты должны быть независимы от реального Keitaro.

## 9. Проверка на реальном Keitaro

Разрешённые операции проверяются отдельно.

Необходимо убедиться, что:

- Кампания действительно создаётся.
- Оба потока присутствуют.
- Фильтры и маршрутизация соответствуют ТЗ.
- Изменения редактора корректно публикуются.
- Полученные после Push данные соответствуют ожидаемым.

Не выполнять операции записи в реальные объекты без явного разрешения.

Известное ограничение тестового окружения: текущему API-пользователю может быть доступен только один оффер, а создание дополнительных ограничено правами.

Это не должно препятствовать автоматизированной проверке логики работы с несколькими офферами.

## 10. Критерии приёмки

Функциональность считается выполненной, когда:

1. Creator создаёт кампанию с правильными двумя потоками.
2. Домен, группа и источник назначаются через API.
3. Editor загружает потоки и корректно отображает офферы.
4. Add / Remove / Bring Back работают в соответствии с видео.
5. До Push изменения не попадают в Keitaro.
6. Cancel отменяет неопубликованные изменения.
7. Удалённые офферы не теряются из локальной истории.
8. Fetch Streams корректно учитывает внешние изменения.
9. Pin сохраняет закреплённые веса.
10. Сумма активных весов равна 100% с учётом точности API.
11. Автоматизированные тесты проходят.
12. Проект можно запустить по README.

## 11. Сдача проекта

Репозиторий GitHub должен содержать:

- Исходный код.
- README с инструкцией запуска.
- Инструкцию по настройке переменных окружения.
- Инструкцию по миграциям.
- Автоматизированные тесты.
- Краткое описание реализованных возможностей.
- Описание ограничений тестового окружения.

API-ключи, токены и локальные секреты не должны попадать в репозиторий.

## 12. Технические решения, не заданные напрямую

Следующие детали являются решениями разработчика, а не дословными требованиями заказчика:

- Разделение на маршруты `/creator` и `/editor`.
- Модульный монолит.
- Автоматический fallback домена.
- Конкретная структура SQLAlchemy-моделей.
- Способ разрешения конфликтов при Fetch Streams.
- Точность и алгоритм округления весов.
- Автоматическая постпроверка после создания кампании.
- Дополнительный Demo-режим.

Эти решения должны быть документированы и не противоречить основному ТЗ.

Приоритет разработки: **корректная бизнес-логика → API-интеграция → хранение состояния → тесты → визуальные улучшения**.
